# 变更范围与原因

作者：chenjixian

## 1. 需要解决的问题

专家的可见范围、创建者与实际使用者是不同概念。多人可以使用同一个专家定义，不代表应该共用文件、个人记忆、会话数据库或执行身份。仅在 HTTP 接口检查专家归属，无法替代命令、终端、本地 MCP 和文件工具的低权限执行边界。

本次改动围绕以下目标展开：

| 目标 | 对应变化 | 为什么需要 |
| --- | --- | --- |
| 共享专家、内容私有 | 按使用者和专家主键选择运行实例 | 防止共享定义连带共享使用过程中产生的内容 |
| 文件访问有操作系统边界 | 每个平台账号分配低权限 UID，文件操作通过 worker | 防止服务进程使用自身高权限替用户访问不属于该用户的文件 |
| 身份贯穿全部调用阶段 | HTTP、WebSocket、网关、普通调用及审批恢复绑定使用者 | 防止流响应、异步线程或恢复执行丢失用户身份 |
| 私有内容可显式协作 | 指定接收账号的只读文件快照 | 满足分享需求，同时保留原工作区的私有权限 |
| MCN 导出结果能交付给聊天用户 | 导出创建返回任务 ID 和文件名 | 让聊天工具继续查询对应异步任务的下载结果 |
| Octop 子路径下资源能被正确路由 | 对已知根路径资源重写到 `/aiwork/` | 避免头像、插图和图标落到 ERP 的默认页面 |

上述原因由现有实现和关联资料归纳；未确认的文件变化原因单独标注，不推断作者意图。

| 实现位置 | 观察到的变化与原因 |

| [repair.py](../../src/octop/infra/isolation/repair.py) | 新增受控 owner、mode、默认 ACL 修复与 `.isolation-repairs.jsonl` 日志，保留修复前元数据；避免将所有历史权限差异都变成只能手工处理的启动故障 |

新增逻辑的核心是：兼容性修复或维护页面不改变低权限执行身份，隔离不就绪时不执行用户任务。由于源文件仍在并行变动，本轮只对上述已读取部分做静态记录，未完成其全部分支、兼容和运行验证。

## 3. MCN ERP 的关联变化

### 3.1 导出创建返回任务身份

修改文件：[DeliveryDashboardController.java](../../../huihuo-mcn/src/xiaogj-youli-mcn/xiaogj-youli-mcn-service/src/main/java/com/xiaogj/youli/mcn/api/controller/delivery/DeliveryDashboardController.java)。

- 入口为 `POST /api/mcn/deliveryDashboard/link/export` 和 `POST /api/mcn/deliveryDashboard/project/export`。
- 原成功结果为 `data: true`；现成功结果为 `data: { taskId, fileName }`，`taskId` 按字符串返回。创建任务返回空时仍为 `data: false`。
- `createExportTask` 仍先创建任务，再调度异步导出。返回对象只代表已接受任务，不代表文件已经生成，也不是直接返回下载地址。
- 任务创建仍使用当前用户的 `companyId`、`employeeId`；该 diff 没有修改查询 SQL、表结构或租户条件。

相关已有代码：[delivery_export.py](../../src/octop/infra/auth/youli/delivery_export.py) 的 `export_delivery_result` 解析任务 ID，再由 `_poll_download` 查询任务列表并按 ID 匹配，读取 `downloadFile`。这是与本次 Java 返回值配套的已有消费端，不属于当前未提交 diff 的新增文件。任务列表当前只查前 20 条，因此返回任务 ID 也不保证一定能立即查到任务，仍需验收任务较多和异步失败场景。

已核对的 ERP 页面调用方：[delivery-dashboard.vue](../../../huihuo-mcn/src/xiaogj-youli-mcn-frontend/src/jinbeiguanjia/views/hui-huo/service-management/delivery-dashboard.vue) 的 `exportLinkData`、`exportProjectData` 只将 `data === false` 判为失败，成功返回对象仍走原成功分支。这只证明这两个直接页面调用方的静态兼容，不能推导为所有外部客户端兼容。

### 3.2 根路径静态资源兼容

修改文件：[edge-locations.conf](../../../huihuo-mcn/docker/nginx-edge/include/edge-locations.conf)。

Octop 页面部署在 `/aiwork/`，但部分资源仍按根路径引用。新增规则将下列请求重写为 `/aiwork` 加原 URI，再重新匹配 location：

- `/experts/avatars/` 目录。
- `/assets/mbti/` 目录。
- 明确列出的 `octop-mascot-*` 和 `pwa-192.png`、`pwa-512.png` 文件。

核心是修复已知资源的入口路径；未新增整个 `/assets/` 的通配接管。Nginx 配置加载、真实资源返回及与现有 location 的交互，本轮均未运行验证。

## 4. 应单独识别的其他状态

| 类型 | 观察到的事实 | 原因与处理边界 |
| --- | --- | --- |
| 可执行位变化 | 三个仓库合计 105 个文件只有 `100755 → 100644`，文本内容无 diff | Windows 检出或拷贝可能造成此现象，但未确认实际来源。会影响 Linux 直接执行，不能当作业务逻辑改动或直接认定无影响；本轮不修改这些状态 |
| 符号链接删除 | `src/octop/infra/agents/experts/library/cvm-cluster-doctor/skills/cvm-ai-doctor` 的 Git 模式为 `120000`，原目标为 `../../cvm-ai-doctor/skills/cvm-ai-doctor` | 删除原因未确认，与本次用户隔离目标没有直接证据关联；不能自行归类为必要删除 |
| 临时产物 | `.pytest-release-*`、`.pytest-unify-final/`、`.tmp_pytest*/`、`.tmp_tools/`、`.tmp_mcn_adapter_smoke.py`、`.tmp_pytest_out.txt` | 测试或排查线索，不能仅凭目录名认定测试通过；不作为正式功能实现，本轮不删除 |
| hh-ai-creator | 7 个脚本仅有模式变化 | 当前没有文本业务改动，不能虚构其与隔离功能的实现关系 |

数据库结构、索引和 `company_id` 查询未因上述隔离/分享 diff 新增变更。分享元数据复用 `settings` 的 `isolation.file_share.` 键；个人实例配置使用 `isolation.runtime_config.` 键，记忆强制使用实例私有 SQLite。文件与远程业务的隔离维度仍需分别核实。
